# 列車通過判讀（TrainWatch）

從固定攝影機的長時間錄影，判讀列車車頭到達、車尾離開參考線的時間與方向。
Windows 免安裝版由 GitHub Actions 自動打包（`.github/workflows/build.yml`），使用者不需要安裝 Python。

免安裝版的結構（v1.0.1 起）：

```
列車通過判讀_v1.0.1/
  啟動列車通過判讀.bat   ← packaging/start.bat（只能用 ASCII：cmd 以系統字碼頁讀 .bat）
  使用說明.txt
  監測站設定/            ← v1.0.8 起不再使用（build.yml 仍會建立；程式會在裡面放「這個資料夾已不使用.txt」）
  runtime/               ← Python 官方 embeddable 3.11.9＋從同版本完整 Python 複製的 tkinter＋site-packages
  app/                   ← main.py、trainwatch/
```

**不要改回 PyInstaller**：v1.0.0 用 PyInstaller 做的 TrainWatch.exe 沒有數位簽章，被使用者公司的防毒（趨勢科技 Apex One 機器學習偵測）
判成 Troj.Win32.TRX.XXPE50FFF110 隔離。改用官方簽章的 python.exe／pythonw.exe 後，打包流程會檢查簽章有效才產出。

- 使用者操作說明：`docs/使用說明.md`（打包時會複製成 `使用說明.txt` 放進 zip）
- 修正紀錄（唯一的一份）：`docs/修正清單.md`

## 開發與測試

```
pip install -r requirements.txt
python main.py
python -m unittest discover -s tests -v
TW_SAMPLES=D:\樣本影片 python -m unittest discover -s tests -v
```

**樣本影片與 `expected.json`（逐格核對過的答案）都是使用者的監測資料，不可以放進 repository**（`.gitignore` 已排除 mkv/mp4/avi 與 expected.json）。這個 repository 是公開的，說明與範例一律用假日期。

## 判讀流程（core.Detector.feed，每一格）

1. 只處理參考線＋軌道範圍的外框（`work_crop`），灰階＋高斯模糊。
2. 亮度修正：整個畫面縮小（每 8 點取 1 點，綠色頻道），軌道範圍 ±20 px 與上方 40 px（字幕）以外的區域，目前 ÷ 背景的中位數＝攝影機自動調亮度倍率，先除掉再比較。
3. `score`＝參考線遮罩上 |畫面−背景| 的平均。超過 `on_level`（15）開始一筆，低於 `off_level`（10）超過 `merge_gap`／2 秒才結束。
4. **列車停住不算離開（v1.0.4）**。事件結束的條件只有一個：參考線上的變化量低於 `off_level`，而且連續 `max(merge_gap, 2 秒)` 都沒有回升；車尾時間記在「最後一次還被佔用」的那一格（不含等待確認的 2 秒）。停住只會在備註寫「曾停止約 N 秒」。v1.0.10 起沒有任何「停太久就結束」的條件：完全沒有動靜超過 `max_static`（30 分鐘）只標需確認；攝影機畫面整個改變另外由 `_camera_check()` 處理（見下方 v1.0.10）。「在動」＝參考線上前後兩格平均差 > `static_motion`，或軌道範圍內差 >10 的像素超過 0.4%。
5. 背景：沒有事件時學習（和背景差 < `pixel_diff` 的像素 α=0.02，差很多的像素 α=0.001，慢速列車進站時不會先被學進去）；**事件中完全凍結**，停多久都不會把列車學成背景。第一支影片的初始背景＝開頭 90 秒取 31 格的中位數。**不要改成整支影片的中位數**：傍晚光線一直變，開頭會被誤判成列車（v1.0.4 實測，見修正清單 #32）。
6. **白天光線（v1.0.5）**：畫面彩度 ≥ `day_saturation`（25；夜間紅外線模式是 0）且 score 超過 off_level 時，算參考線帶狀區（遮罩上下擴 10 px）目前畫面與背景的正規化相關（NCC）。> `light_ncc`（0.45）＝只是光線變化，不算佔用；沒有事件時持續 1 秒就直接把背景換成目前畫面。實測：陽光 0.55～0.6、白天列車 −0.2～0.3、**夜間列車 0.77～0.9（所以夜間不能用）**。
7. 結束時（`_close`）：
   - 方向：每一欄「連續變化 ≥0.4 秒」的第一段開頭與最後一段結尾，右側中位數−左側中位數。兩者同號且 ≥0.15 秒＝有把握；只有車頭可判＝不確定。逐格資料保留事件開頭 60 秒＋最後 60 秒，停很久也有車頭、車尾的證據。
   - 車頭／車尾修正（`_refine`）：事件中 score 第 80 百分位的一半為門檻，第一次／最後一次達到的時間才算（處理車燈先照亮、車走後背景殘差）。
   - 排除：時長 < `min_duration`、覆蓋率 < `min_coverage`、參考線兩側同時被擋比例 < `min_both`。

## 驗收測試（tests/test_all.py 的 TestScenarios，假影片）

正常通過、停 5 秒、停 35 秒、兩列車重疊（A 10～30 秒、B 20～40 秒 → 一筆 10～40 秒）、兩列車中間清空（兩筆）、車廂空隙、曝光變化與車燈（無車不可以有事件）、車走後畫面變暗。停 5 秒、停 35 秒兩項對 v1.0.3 的程式會失敗。v1.0.5 加：白天局部陽光（無車不可以有事件）、陽光下有列車；把 `light_ncc` 設成 9（等於關掉）這兩項會失敗。

每次修改判讀邏輯後，**要把全部真實樣本和上一版逐筆比對**（不只看 expected.json 有的那幾支）。

## 輸出檔

- `列車通過紀錄.xlsx`／`.csv`／`results.json`：判讀完自動輸出；第 2 頁修改後按「儲存修改並重新輸出 Excel」。
- 噪音分析程式用 TXT（第 2 頁「輸出噪音分析用 TXT」）：每行 `日期,進入時間,離開時間,10,FR,,A`（例 `2023/09/18,11:01:26,11:01:28,10,FR,,A`），ASCII、CRLF；只含「是列車」的；進入時間無條件捨去到秒、離開時間無條件進位到秒（使用者 2026-10-01 同意）。`10,FR,,A` 是噪音程式固定要的欄位（`export.NOISE_SUFFIX`）。

## 影片數量與效能（v1.0.4）

- 一次最多 300 支（`gui.MAX_FILES`）且合計 48 小時（`gui.MAX_HOURS`，v1.0.5）。加入時不開檔，影片資訊與畫面時間在背景讀，每讀完一支只更新清單那一列（以前整個清單重畫，300 支就重畫 300 次）。
- 實測（這台雲端電腦）：10 分鐘影片判讀約 10 秒；300 支（50 小時）預估 50～100 分鐘。截圖與短片另外每支多約 4 秒（每秒格數和檔頭不符的影片）。

## 截圖、短片與預覽（v1.0.3 起）

- 有些影片實際每秒格數和檔頭不同（檔頭 15、實際 10），OpenCV 的 `CAP_PROP_POS_MSEC` 跳轉會跳錯（實測跳 100 秒落在 174～246 秒，結果和這個 VideoCapture 之前做過什麼有關），250 秒以後甚至讀不到畫面。**不要再用跳轉來找截圖或短片的畫面。**
- `save_frames_and_clips()`：每支影片從頭依序 `grab()` 一次，只有需要的格才 `retrieve()`，依每一格實際的時間存截圖、寫短片（跨檔案的短片接在後面）。
- `open_at()`／`read_frame_at()`（預覽、教程式認字）：先試跳一次並檢查實際時間；跳錯就記住這支影片，之後都從頭依序讀。

## 結果資料夾位置（v1.0.6）

- `<存放位置>/判讀結果/<監測站>_<YYYYMMDD_HHMMSS>/`；`gui.result_root(location, first_video)`：location＝None 為第一支影片的資料夾；選的資料夾本身叫「判讀結果」就不再多包一層。
- 預設位置存在 `data_dir()/程式設定.json`（v1.0.7 以前在 `app_dir()`）（`{"result_location": 路徑或 null}`），寫不進去改存使用者資料夾 `列車通過判讀_程式設定.json`。`out_location`（這次）與 `out_default`（預設）分開，「只用這一次」不寫檔。
- 開始判讀前檢查位置存在；取消時只刪這次才建立的空資料夾（`_made_root`），使用者自己建的空「判讀結果」不刪。
- 第 1 頁左欄：「判讀」區用 `side='bottom'` 先排、影片清單內下方幾行也先排，視窗最小（1200×760）時縮的是影片清單，不會把開始判讀、狀態列擠出畫面。

## 監測站的攝影機位置基準、幾何位置（v1.0.13，修正清單 #82～#87）

- 儲存監測站時，用畫參考線的那個畫面存一張位置基準（`Profile.camera_anchors`，灰階 JPEG base64，最多 8 張，第一張保留）。`profile_version`＝2；沒有這個欄位的＝1（舊版）。results.json 只記張數（`camera_anchor_count`），另記 `app_version`。
- 比較方法：ORB 特徵點＋RANSAC（`estimateAffinePartial2D`），量參考線兩端、中點與軌道範圍四個角實際偏了幾像素（取最大）。符合點 < 40＝比不起來；< 3 像素＝相同；≥ 6＝移動；中間＝無法確認。
  - 真實樣本：同一支影片 10 分鐘內每次都比得起來（符合點 127～1227）、偏移最大 0.8；夜間相隔約 5 小時 ≤ 0.1；白天上午↔下午、白天↔夜間比不起來（≤ 27）。
- 判讀前 `check_start()`：第一支影片與之後每次白天／紅外線切換的第一支（第 1 秒畫面）和基準比。moved→不判讀；none（舊版監測站）／uncertain→並排顯示兩張畫面請使用者確認，確認的畫面加進基準並存回監測站設定。
- 判讀途中 `CameraGuard._geo()`：每 30 秒和比較畫面比，偏移＝比較畫面本身的偏移＋這次量到的；符合點 < 80 就換新的比較畫面（偏移量保留，不歸零，不是逐次累加）。連續兩次 ≥ 6 像素→停止（kind=drift）；比不起來就和監測站基準比；超過 5 分鐘都比不起來→停止（kind=uncertain）。第一格就和監測站基準比，不同→停止（kind=profile，沒有任何事件）。
- 相位相關（下面 v1.0.12）照舊負責突然被碰歪；它 60 秒比不起來時，只有幾何這一層剛確認位置相同才重建。
- `gap_check()` 改用幾何這一層；沒有任何位置可比＝uncertain。
- **不停止判讀（使用者 2026-10-03，#88，取代下面 v1.0.11 的「停止判讀」）**：攝影機位置有問題一律記在 `Detector.camera_events`、`guard.rebase()` 後繼續；`_wrap_up()` 把之後（含當時通過）的列車標需確認（`_mark_after_camera`）。突然被碰歪（moved）：當下那一筆結束，暫存接下來 `WARM`（10）秒的畫面建背景（`flush_warm`），再把這段畫面補判讀。`info['camera']`＝第一次、`info['camera_events']`＝全部。
- 影片讀取出錯（#87、#88）：跳過那支剩下的部分，下一支當成錄影中斷；`info['errors']`。第一支就打不開且沒有任何影片可判讀才丟出錯誤。
- 判讀前 `check_start()` 結果 moved 時，畫面讓使用者選「回去重設參考線」或「仍要判讀（全部標需確認）」。
- 可接受誤差（使用者 2026-10-03）：車頭進入、車尾離開參考線 1.5 秒以內 → `REFINE_CHECK`＝1.5。

## 攝影機位置基準（v1.0.12，修正清單 #74～#79）

- `CameraGuard`：和列車背景分開的攝影機位置基準。軌道以外畫面的邊緣強度圖（縮 1/2），`cv2.phaseCorrelate` 量平移。
  - 基準＝批次開頭 2 秒 5 格中位數；每 2 秒在「平移 < 1 像素且 r ≥ 0.3」時換成目前畫面；疑似移動期間凍結；`Detector.restart()`（錄影中斷）不動它。
  - 移動＝平移 ≥ 6 像素且 r ≥ 0.15 開始懷疑，之後平移穩定（差 < 3 像素）5 秒就確認。**不要用「r 變低」當證據**：白天有風時 r 10 秒內就會掉到 0.5 以下。
  - 超過 60 秒無法更新又沒有平移（例如彩色↔紅外線）→ 重新建立基準，寫進 `notes`（品質摘要、Excel）。
  - 錄影中斷：`gap_check()` 比對中斷前基準與下一支影片前 2 秒 → same／moved／uncertain，後兩者停止（`info['camera']['kind']='gap'`）。
  - v1.0.10／v1.0.11 的「縮 8 倍畫面紋理相關 < 0.35」在真實畫面上幾乎偵測不到（實測移動 14×9 像素＋轉 1.5 度仍有 0.77～0.91），已換掉。
  - 只能和幾秒前的畫面比：白天有風時，間隔幾分鐘 r 就掉到約 0.05（v1.0.13 實測；v1.0.12 說明寫「間隔 10 分鐘 r ≥ 0.74」是錯的）。
- 第 2 頁「手動新增列車…」（`manual_add`），檔名前綴 M001…。
- 測試的暫存資料夾在全部測試跑完後刪掉（`_mkdtemp`），不然假影片會把磁碟塞滿。

## 攝影機位置改變就停止判讀（v1.0.11，修正清單 #71；v1.0.13 起改成繼續判讀，見上方 #88）

- `_camera_check()` 偵測到 → 進行中的那一筆 `finish('camera')` → `self.camera_stop`；`process(info=)` 看到就停止，`info['camera']=dict(t, file, pos)`。GUI 把說明寫進該影片的 `timing['stop']`，品質摘要、Excel、results.json 都會出現。
- **不可以重建背景後繼續判讀**：參考線、軌道範圍是固定像素位置（v1.0.10 的做法已撤回）。自動影像配準暫不做。

## GPT 第三輪檢查的修正（v1.0.10，修正清單 #66～#70）

- `finish()`：事件還在就一律 `end_known=False`，含「正在等確認」（`pending_close`，`confirming=True`）。
- **不再因為 `max_static` 結束事件**，只設 `static_alarm`（需確認）。取而代之的是 `_camera_check()`：`_exposure_calc` 順便算軌道以外的紋理相關 `_out_ncc`，< `CAM_NCC`（0.35）持續 `CAM_SEC`（5 秒）→ 結束進行中的那一筆（`incomplete='camera'`；畫面改變那一刻才開始的 → 不是列車）。（v1.0.10 之後會重建背景繼續判讀；v1.0.11 起改成停止判讀，見上方。）
- `process()`：下一支影片比上一支實際結尾早 > `OVERLAP_SEC`（2 秒）→ `TimeOrderError`。
- 截圖：`start_known`／`end_known` 為 False 時叫「1第一畫面_車頭未確認」「3最後畫面_車尾未確認」。
- **被否決或撤回的建議統一記在 `docs/修正清單.md` 最後的表，修改前先對照。**

## GPT 第二輪檢查的修正（v1.0.9，修正清單 #45～#64）

- **車尾未確認**（`end_known=False`）：`Detector.finish(why)` 在影片結束（video_end）、取消（cancel）、錄影中斷（gap）時參考線上還有車；（v1.0.9 還包括 30 分鐘保險，v1.0.10 已拿掉，見上方）。一律需人工確認、備註寫原因、不做車尾 `_refine`。
- **錄影中斷**：`process()` 用每支影片實際讀到的最後一格算間隔，> `GAP_SEC`（5 秒）→ `finish('gap')`＋`Detector.restart()`（背景重建、不延續上一格與歷史）。
- **初始背景**：`initial_background()` 另取整支影片中位數比對；參考線上差異 > on_level 只標「背景不確定」（`BG_UNSURE`），**不要改用整支影片的背景**：「開頭停著後來開走」和「後來開進來停到結束」畫面對稱，改用會讓後者出錯（test47／test56）。
- **紋理範圍**：`Detector.band` 依軌道方向加寬（上下走向用 21×1）。
- **截圖與短片**：`save_frames_and_clips(..., bases=)` 依畫面時間把短片切成每支影片的一段（跨 3 支以上不會漏）；> `LONG_CLIP`（60 秒）只做頭尾各 `CLIP_PART`（10 秒）；已排除不做短片，第二張截圖是 `peak_*`（變化最大）；檔名前綴 `media_tag` 第一次產生後固定。
- **介面**：畫面大小不一致直接擋（`check_sizes`）；正式校正後 `final_order()` 排序、重疊就停；`mark_time_jumps()`；`quality_summary()`；重做截圖短片時只改副本、期間擋套用／儲存（`_media_busy`）；`_locate()` 不吸附缺口。
- results.json 新增：`end_known`、`media_tag`、`peak_t/peak_file/peak_pos`、`start_shift/end_shift`、`check_items`（品質摘要的分類，和備註同時寫）。
- 假影片產生器 `make_scene` 新增 `vertical`（轉 90 度）與 `ir_at`（切紅外線）。

## 設定的位置（v1.0.8）

- `gui.data_dir()`＝「文件」（Windows 用 `SHGetFolderPathW(CSIDL_PERSONAL)`，資料夾被搬到 D 槽／OneDrive 也找得到）`\列車通過判讀設定`，裡面是 `監測站設定\*.json`、`_上次使用.txt`、`程式設定.json`、`_已詢問匯入舊版設定.txt`。測試用 `TRAINWATCH_DATA` 指定別處。
- 啟動時：新位置沒有監測站、程式資料夾的 `監測站設定` 有 → 自動複製過去（`_migrate_from_app_dir`）。都沒有、也沒問過 → 問一次「選擇舊版資料夾…／重新設定」（`_first_run_check`，`CI=true` 時不問，GitHub Actions 的視窗測試才不會卡住）。
- `find_old_settings()` 接受舊版程式資料夾或直接選「監測站設定」資料夾；`import_settings()` 同名不覆蓋。
- **build.yml 沒有改**：打包時仍建立空的 `監測站設定`，而且 GUI 測試之後的 `Get-ChildItem "$env:DST/監測站設定"` 需要這個資料夾存在（`$ErrorActionPreference='Stop'`），所以程式不可以刪掉它。

## 視窗縮小（v1.0.7）

- 兩頁都包在 `ScrollArea`（Canvas＋內框）：可視範圍比內容需要的（`winfo_reqwidth/reqheight`，每 0.4 秒檢查一次）小時，內框維持需要的大小並顯示捲軸；夠大時內框跟著視窗伸縮。`root.minsize(640, 420)`。
- 因為要量得出內容需要多高，左欄（寬 360）與第 2 頁右欄（寬 500）**不要用 `pack_propagate(False)`**，改用 1 px 高的空框撐寬度；第 2 頁清單框才用 `pack_propagate(False)`（最少 420×200，比這窄用清單的水平捲軸）。
- 第 1 頁影片畫面大小＝`self.cw/self.ch`（Canvas 的 `<Configure>`），畫面下方各列 `side='bottom'` 先排，畫面拿剩下的空間。
- 滾輪：`bind_all`，在 Treeview／Combobox／Spinbox／Scale 上不捲整頁。
- 驗收時要截圖看 1320×820、1200×760（不可以有捲軸）、960 寬（不可以左右捲）、800×560（捲到底每個按鈕都看得到）。

## 修改時間後重做截圖與短片（v1.0.5）

第 2 頁「套用修改」若車頭／車尾時間有改：`_locate()` 用 run_files／run_timing 把畫面時間換回（影片, 影片內秒），背景執行緒呼叫 `core.save_frames_and_clips([e], …)` 只重做這一筆；`media_busy` 時「播放短片」等做好再播（`regen_done`）。「在影片中看這段」用新的 start_pos − 2 秒。

## 時間（osd.py）

- 不使用檔名。`calibrate()`：開頭 20 秒每一格＋整支平均 30 個點各 3 格，讀出畫面時間；每一格與次佳字樣的相關係數差 < 0.03 的不採用。
- `(畫面秒 − 影片內秒)` 的整數投票取眾數（相鄰兩個整數合併），一致率 < 80% 視為失敗。
- 小於 1 秒的對齊：取這些值的第 97 百分位（秒數跳號那一刻的上緣）。
- 內建字樣是從使用者攝影機（640×360，白字黑邊，字距 10 px，外框 [14,8,204,24]）學來的 10×16 灰階圖，以 base64 內嵌。
- 「教程式認字」（`learn()`）：使用者輸入某一格畫面上的時間，往後讀 13 秒，以最後一位秒數變化遞增當答案，收集 0～9。

## 驗證紀錄（v1.0.0，使用者提供的 10 支樣本，白天 6 支、夜間 4 支）

- 畫面時間：10 支一致率 100%；其中 1 支檔名比畫面晚 1 秒（證明不能用檔名）。
- 有效列車 15 筆：白天 9 筆車頭、車尾以每 0.2 秒一張的放大截圖核對（誤差約 0.2 秒以內）；夜間 2 筆的時間與方向和使用者告知的一致（含 1 筆單節機貨車）。
- 已排除：道路上的貨車與汽車、路燈閃爍、路上車燈照亮參考線一側。
- 突變測試：把 `min_both` 設 0、或關掉亮度修正，回歸測試都會失敗。

## 發布

1. 改 `trainwatch/gui.py` 的 `VERSION`。
2. 上傳到 GitHub（main）→ Actions 自動跑單元測試、組出免安裝資料夾、檢查 Python 數位簽章，再用資料夾裡的 Python 跑 `--selftest` 並實際開一次視窗。
3. Actions 該次執行頁面最下方 Artifacts 下載 `TrainWatch_v版本_windows.zip`（只包一層，解壓縮一次）；推送 `v1.0.1` 這種標籤則另外建立 Release。
